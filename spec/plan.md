# Agent Comms Implementation Plan

## 1. Product Shape

Build Agent Comms as a local MCP server that owns short-lived collaboration channels. The server is the neutral mailbox and event log; the coding agents remain responsible for reasoning, editing files, and deciding when their own participation is complete.

The initial implementation should optimize for correctness and a small, composable MCP surface rather than transport sophistication. MCP calls are sufficient for sending messages and reading history. A blocking wait method can provide efficient coordination without requiring every client to understand a separate event protocol.

### Recommended interaction model

Use a hybrid receive API:

- `comms_poll`: return immediately with messages after a cursor.
- `comms_wait`: wait until a matching message is available, the timeout expires, or the channel is closed.

Polling is useful at natural checkpoints and for clients that cannot hold a request open. Waiting is the default for an agent whose next action depends on another participant. Both methods use the same cursor and filtering semantics, so they are two attention modes over one mailbox rather than two separate messaging systems.

Do not make "return from the subagent" a server concern in v1. A subagent can use a final message to announce completion, and the primary agent can close the channel when it has enough information. This preserves the stated ownership boundary: agents decide when to return; the hub records and delivers communication.

## 2. Domain Model

### Channel

A channel is an isolated collaboration room.

Suggested fields:

- `channel_id`: opaque, unique identifier.
- `name`: human-readable label.
- `mission`: concise description of the shared objective.
- `status`: `open` or `closed`.
- `created_at`, `closed_at`.
- `workspace_root`: optional normalized project root used to validate attached paths.
- `participants`: registered agents and their roles.
- `next_sequence`: monotonically increasing message sequence.

Channels should have explicit lifecycle operations. Closing a channel prevents new messages and releases waiters; history remains readable after close for final synthesis.

### Participant

Participants are logical identities, not MCP connection identities. In the initial OpenCode integration, several subagents may invoke the same MCP server through the same host process and connection. The hub therefore cannot independently prove which subagent is making a call. The coordinator requests a participant registration, the hub assigns the identity and generates its credential, and the coordinator passes that credential into the corresponding subagent's task context.

A participant should have:

- `agent_id`: stable within the channel and assigned by the hub, or requested by the coordinator if available.
- `display_name`: readable name used in prompts and history.
- `role`: responsibility, such as `reviewer`, `test investigator`, or `API implementer`.
- `participant_token`: opaque, cryptographically random, channel-scoped bearer credential generated by the hub during registration.
- `status`: `active`, `idle`, `completed`, or `left`.
- registration and last-seen timestamps.

The channel creator is the `coordinator`. The coordinator may register participants, close the channel, and read all history. A participant may read channel broadcasts and messages addressed to it, and may publish as itself. This is a cooperative attribution and routing model, not a security boundary between trusted subagents in one agent runtime.

The hub, never the coordinator or subagent, generates `participant_token` at registration. The token is returned to the coordinator over the registration response so the coordinator can place it in the intended subagent's task context. The token must not be included in channel messages, history, or broadcast content.

### Message

Every message is append-only and receives a channel-local sequence number.

Suggested fields:

- `sequence`: the resume cursor and total ordering key.
- `message_id`: globally unique identifier for diagnostics and idempotency.
- `channel_id`.
- `sender_id`.
- `audience`: `broadcast` or a target `agent_id`.
- `body`: concise text, with structured metadata kept separate.
- `attachments`: zero or more project file references.
- `created_at`.

The ordering guarantee is channel-wide append order. Delivery visibility is audience-specific: a direct message is visible to its sender, recipient, and coordinator; a broadcast is visible to all participants. This makes the full coordinator history genuinely full without exposing private direct messages to unrelated agents.

### File attachment

Attachments are references, not uploaded content.

Suggested fields:

- `path`: workspace-relative path as the canonical display form.
- `kind`: `context`, `working`, `handoff`, or `review`.
- `note`: optional explanation of why the path matters.

The server should reject paths that are absolute, escape the configured workspace root, or do not satisfy the chosen existence policy. v1 should validate path shape and workspace containment; it need not snapshot file contents or lock files. The message can state that an attachment is expected to exist when shared, leaving strict existence checking configurable for agents that announce future work.

## 3. MCP Tool Surface

Names are provisional and should be finalized against the MCP SDK conventions selected during implementation.

### `comms_create_channel`

Creates an open channel and registers the coordinator.

Inputs:

- `name`.
- `mission`.
- optional `workspace_root`.
- optional coordinator display name.

Returns the channel summary, coordinator identity, hub-generated coordinator credential, and an initial cursor. The coordinator credential is separate from every participant token and is required for coordinator-only operations.

### `comms_register_agent`

Adds a participant to an open channel.

Inputs:

- `channel_id`.
- optional requested `agent_id`.
- `display_name`.
- `role`.

The hub generates the `agent_id` if one is not supplied and always generates a fresh `participant_token`. The response returns the registered participant identity and token to the coordinator. The subagent does not call registration and cannot choose its own token.

Registration should be idempotent only when the coordinator supplies an explicit client registration key and retries the same request. A repeated registration without that key should create a new participant credential rather than accidentally reusing or exposing an existing token. Conflicting labels or roles should be rejected unless an explicit update operation is added later.

### `comms_send`

Appends a message.

Inputs:

- `channel_id`.
- `participant_token`.
- `body`.
- `audience`: broadcast or one target participant.
- optional `attachments`.
- optional `client_message_id` for retry-safe submission.

The hub resolves `participant_token` to the sender identity and rejects tokens from another channel or participant. The result returns the assigned sequence, message ID, and normalized attachment paths.

### `comms_poll`

Returns currently available visible messages after a cursor.

Inputs:

- `channel_id`.
- `participant_token`.
- `after_sequence` (default 0 for a new reader).
- optional `limit`.
- optional `include_own_messages` (default true).

The response includes messages, `next_sequence`, channel status, and whether more visible messages remain. A cursor is a position in the channel log, not a count of messages visible to the reader; clients must always advance using the returned sequence.

### `comms_wait`

Waits for the first available visible message after a cursor, or returns on timeout/channel closure.

Inputs:

- the same reader and cursor inputs as `comms_poll`.
- `timeout_ms`, bounded by a server maximum.
- optional `limit` to return a batch once awakened.

The response should distinguish `messages_available`, `timeout`, and `channel_closed`. A timeout is normal control flow, not an error.

### `comms_history`

Returns a full or bounded history for the coordinator, with optional filters by sender, audience, attachment path, or sequence range. The coordinator authenticates with its channel-management credential. Participant access should remain limited to messages visible to that participant and authenticated with its participant token.

Inputs should support pagination or `after_sequence` plus `limit`; never require unbounded history in one response.

### `comms_set_status`

Updates a participant's lifecycle status, especially `completed`, `idle`, and `left`. This is a convenience signal for coordination and observability, not a termination primitive.

### `comms_close_channel`

Closes the channel, wakes pending waiters, rejects future sends, and preserves history for reads. The close response should include participant statuses and message counts to help the coordinator produce a final summary.

## 4. Delivery and Cursor Semantics

Use an append-only in-memory or persisted log with a per-channel monotonic sequence. A receive operation computes visibility from the reader identity and audience, then returns messages with `sequence > after_sequence`.

This cursor design deliberately tolerates gaps. If sequence 8 is a direct message for agent A and agent B reads after sequence 7, B may receive sequence 9 next. Clients must not assume sequences are contiguous in their personal inbox.

For `comms_wait`, register a waiter against the channel before checking the log a second time. This avoids the classic race where a message arrives between the initial read and waiter registration. On append, notify all waiters in the channel; each waiter re-evaluates audience visibility and cursor position before returning. On timeout, remove the waiter and return a typed timeout result.

Delivery is at-least-once from the client's perspective because an agent may retry a receive call after a timeout or transport failure. The cursor is the deduplication mechanism. Sending should support an optional client-generated idempotency key so a network retry does not append duplicate messages.

## 5. Storage and Runtime

### v1 default

Use a single local server process with an in-memory channel store and an optional append-only JSONL journal. Keep the storage abstraction behind a small interface so SQLite can be introduced without changing tool behavior.

The default should be memory-first because channels are session-scoped, startup should be fast, and no project files should be modified merely by running the MCP. Persistence is valuable for postmortems and process restarts, so make it an explicit configuration option rather than silently promising durability.

### Persistence considerations

If journaling is enabled:

- Store channels and messages under a user-owned runtime directory, not the project workspace.
- Write records in append order and recover only complete records on startup.
- Treat the journal as sensitive: messages may contain source-code context, paths, or secrets accidentally pasted by an agent.
- Define retention and cleanup behavior before enabling persistence by default.

Do not use a file lock as the primary synchronization mechanism if the server is single-process. If multi-process support becomes a requirement, move to SQLite with transactions and a notification strategy rather than extending ad hoc file coordination.

## 6. Security and Safety

The server is local, but local does not mean risk-free. Implement:

- A hub-generated participant token on every participant send and read.
- Secret scrubbing on every stored message body, attachment path, attachment note, and client message ID; coordinator and participant credentials are replaced before persistence or history delivery.
- Channel membership checks on every operation.
- Coordinator-only history of all direct messages.
- Workspace-root containment checks for file attachments.
- Bounded body size, attachment count, history page size, and wait duration.
- Safe defaults for journal permissions and cleanup.
- No file contents returned from an attachment operation unless a future feature explicitly adds that capability.

The MCP process should not infer identity from connection state that does not exist. In the first integration, the invoking coding agent must provide its hub-generated `participant_token` on each operation. The server resolves the token to the registered participant, verifies channel membership, and applies that participant's permissions. The server should describe this as a bearer capability for reliable attribution and routing, not as protection against a malicious participant sharing a process with the server. A future OpenCode-specific integration could provide host-attested subagent context, but the generic MCP server should not assume it exists.

## 7. Agent Workflow

Document a recommended prompt/tool loop for integrations:

1. The coordinator creates a channel with a mission and workspace root.
2. The coordinator registers each subagent with a stable ID, name, and role.
3. Each subagent announces its plan and any initial working paths.
4. Agents work, poll at natural checkpoints, or wait when blocked on a teammate.
5. Agents broadcast discoveries that affect shared assumptions and direct questions to the smallest useful audience.
6. Agents mark themselves `completed` and send a concise final handoff with relevant file attachments.
7. The coordinator reads history, resolves remaining conflicts, and closes the channel.

The integration guidance should emphasize that Agent Comms does not make concurrent edits safe. Agents should communicate ownership before editing shared files and use the coding agent's normal diff, test, and version-control tools to resolve conflicts.

## 8. Delivery Phases

### Phase 1: Core room

- MCP server bootstrap and local configuration.
- Channel creation, registration, send, poll, history, and close.
- In-memory store with deterministic sequence ordering.
- Broadcast and direct-message visibility.
- Unit tests for authorization, ordering, cursors, and lifecycle.

### Phase 2: Efficient coordination

- Blocking wait with timeout and close wake-up.
- Participant status updates.
- Idempotent sends and waiter race tests.
- Integration test with one coordinator and multiple simulated agents.

### Phase 3: Project context and resilience

- Workspace-root-aware file attachments.
- Attachment filtering in history.
- Optional journal persistence and crash recovery tests.
- Operational limits, structured diagnostics, and cleanup policy.

### Phase 4: Integration quality

- Example OpenCode-style coordinator and subagent prompts.
- Human-readable history rendering.
- Compatibility checks against the MCP client/runtime versions in use.
- Performance tests for many participants, long histories, and simultaneous waiters.

## 9. Testing Strategy

Test behavior at three levels:

- **Unit:** channel state transitions, visibility rules, path normalization, cursor progression, idempotency, limits, and timeout outcomes.
- **Concurrency:** messages arriving during waiter registration, simultaneous sends, multiple readers, close while waiting, and retries.
- **MCP integration:** invoke tools through the actual server transport and verify serialized schemas, errors, pagination, and reconnect behavior.

Important acceptance scenarios:

- A broadcast reaches every registered participant exactly once per cursor progression.
- A direct message is visible to sender, recipient, and coordinator, but not to unrelated participants.
- A participant can safely skip sequences containing messages it cannot see.
- A waiting agent wakes when its targeted message arrives.
- A waiting agent returns a bounded timeout without losing its cursor.
- Closing a channel wakes all waiters and preserves readable history.
- An attachment outside the workspace root is rejected.
- Repeating a send with the same client idempotency key does not duplicate the message.

## 10. Open Decisions

Resolve these during implementation, with conservative defaults:

- **Identity source:** hub-generated participant bearer tokens for v1 versus host-provided subagent context. Start with hub-generated tokens and document that they provide reliable attribution within a cooperative runtime, not isolation from a malicious same-process participant.
- **Durability:** memory-only default versus opt-in JSONL journal. Start memory-only, add journaling after lifecycle semantics are stable.
- **Path existence:** validate only containment by default, with optional existence checking for future-work announcements.
- **History privacy:** coordinator sees all messages; participant direct-message visibility is sender plus recipient. Confirm this policy before publicizing the protocol.
- **Rejoin behavior:** disallow rejoin after `left` in v1 unless a stable agent identity and cursor recovery requirement emerges.
- **Channel limits:** choose practical defaults for participant count, body size, history page size, and maximum wait duration, then expose configuration rather than per-call arbitrary limits.

## 11. Definition Of Done

The first useful release is complete when a local coding agent can create a channel, register multiple role-bearing subagents, exchange broadcast and direct messages, attach safe project-relative paths, wait without busy polling, inspect complete history as coordinator, and close the room cleanly. These behaviors must be covered by automated tests and documented with a runnable example.
